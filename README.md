## 1. 背景・目的

React、コンポーネント設計、状態管理、ドラッグ&ドロップ、ブラウザ保存を、ひとつの小規模アプリとして設計・実装・確認する。

利用者がリスト（列）とカードを使ってタスクを視覚的に整理し、進捗に応じてカードを移動できるアプリを作る。Board・List・Cardとカード移動というTrelloの基本操作モデルを参照するが、Trelloとの機能互換や完全な再現は目的としない。

## 2. 利用者・利用条件

| 項目 | 内容 |

## 3. 対象範囲

### 3.1 今回の対象（MVP）

- 単一ボード上のリストとカードの管理
- リスト・カードの追加、編集、完全削除（確認あり）
- 同じリスト内・別リスト間のカード移動と並べ替え
- キーボードによるカード移動の代替操作
- localStorageへの保存と、再読み込み時の復元
- 保存済みデータがない初回起動時のサンプル表示
- Trello風のボード、横並びリスト、カードの視覚的階層

### 3.2 今回の対象外・将来検討

対象外は、今回の合意範囲を明確にするために記載する。実装予定を保証するものではない。

- 複数ボード、ラベル、期限、説明文、チェックリスト、コメント
- 担当者、検索・フィルタ、リスト自体の並べ替え
- ログイン、共同編集、権限管理、複数端末同期
- バックエンド、データベース、データのバックアップ・復元保証

## 4. 利用シナリオ

利用者は初回起動時のサンプルを確認し、リストとカードを追加・編集・削除する。作業状況に応じてカードをドラッグ操作または代替操作で移動し、次回は保存済みの状態から利用を再開する。

詳細な正常時・例外時のシナリオは、[利用シナリオ](docs/usage-scenarios.md)を参照する。

## 5. 機能要件

機能要件は、[機能要件](docs/functional-requirements.md)でID（FR-01〜）ごとに定義する。主要な機能は、ボード表示、リスト管理、カード管理、カード移動、保存・復元、キーボード代替操作である。

## 6. データ要件

Board、List、Cardの関係と保持項目は、[データ設計](docs/data-design.md)を参照する。顧客・利用者に説明する概念モデルと、localStorageでの保存形式は区別して扱う。

## 7. 画面・操作要件

画面はボード画面の1画面とする。リストを横並びにし、カードを縦に並べ、追加・編集・削除・移動をその画面内で完結させる。

詳細な画面構成、表示状態、Trello風の視覚デザイン要件は、[画面設計](docs/screen-design.md)を参照する。

## 8. 非機能要件

利用環境、操作性、応答性、永続性、信頼性、保守性、アクセシビリティ、セキュリティ、互換性は、[非機能要件](docs/non-functional-requirements.md)で定義する。

## 9. 制約・前提

本MVPはバックエンドを使用せず、ブラウザのlocalStorageへ保存する。このため、データは同じ端末・同じブラウザ内に限定され、ブラウザデータ削除時の復元、共同編集、複数端末同期はできない。

制約、前提、未対応のリスクは、[制約・前提](docs/constraints-and-assumptions.md)を参照する。

## 10. 受入基準（学習完了条件）

- リスト・カードを追加、編集、削除できる。
- カードを同じリスト内・別リスト間で移動できる。
- 空のリストへ移動でき、移動取消時はデータが変わらない。
- 空白だけの名前を登録できず、削除取消時はデータが変わらない。
- 再読み込み後に保存済みの状態を復元できる。
- 保存データの破損または保存失敗時にも画面が停止しない。
- キーボードだけでもカードを移動できる。

## 11. 変更管理

- 要件追加・変更・削除は、目的、影響範囲、対象外からの変更有無を記録してから反映する。
- 要件と設計の不整合を見つけた場合は、先に要件定義書または詳細資料を更新し、実装変更はその後に行う。
- GitHub IssueとPull Requestを使用する場合は、関連する要件IDと確認結果を記録する。
